## Context

The HIS is a React frontend in `web` and a Node.js backend in `api`. It will handle UAE health, identity, insurance, and financial information. The design must therefore support an inexpensive fake-data prototype without allowing a low-cost deployment to be mistaken for a production healthcare environment.

## Decisions

### 1. Application stack

- `web` SHALL use React, Vite, TypeScript, and Tailwind CSS v4. shadcn/ui components, when added, SHALL be committed into this repository and adapted through shared design tokens rather than treated as an opaque UI dependency.
- `api` SHALL use NestJS, TypeScript, and the default Express adapter.
- Local API development SHALL be runnable through Docker Compose. Docker is a development-only execution environment and SHALL use synthetic data only.
- The API SHALL be a modular REST API that publishes OpenAPI contracts. NestJS controllers delegate to application services; business rules do not live in controllers.

**Rationale:** NestJS with Express provides the least-surprising, well-supported foundation for a modular HIS. Fastify remains a later performance option, not an initial requirement.

#### Frontend design system

The frontend design read is an accessibility-critical regulated healthcare product for clinical and administrative users, with a calm, trust-first visual language. Its foundation dials are `DESIGN_VARIANCE: 3`, `MOTION_INTENSITY: 2`, and `VISUAL_DENSITY: 5`. The installed `design-taste-frontend` skill applies to the visual foundation and public-facing surfaces; it does not replace the specialized interaction design needed for dense HIS workflows, data tables, or multi-step clinical forms.

The application SHALL use one customized shadcn/ui system with Radix primitives and Tailwind CSS v4. Generated component source SHALL live under `web/src/components/ui` and remain owned, reviewed, and adaptable in this repository. Feature modules SHALL consume these primitives and semantic tokens rather than copying generated components or introducing a second visual system. Headless utilities required for specialized controls, such as a future data-table engine, do not constitute another visual system when they render through the shared primitives and tokens.

The authenticated application shell SHALL use a compact top bar for the current practice context, primary module navigation, notifications when implemented, user session controls, and sign-out. The initial navigation SHALL appear as accessible Workforce and Roles controls in that top bar; on narrow viewports it SHALL be available through an accessible menu control. The shell SHALL preserve the current practice context while navigating modules and SHALL not put clinical or authorization decisions in frontend navigation state.

The navigation SHALL establish a stable healthcare information architecture before every module is implemented: Dashboard, Patients, Scheduling, Clinical, Operations, Revenue, and Administration are the initial top-level modules. Selecting a module SHALL reveal only its contextual second-level navigation. Until a module has an authorized application capability, its route SHALL present a clear unavailable state and SHALL not imply authorization, display placeholder clinical data, or call a protected module API. Administration SHALL initially contain Workforce and Roles.

The token contract SHALL use semantic names for background, surface, foreground, muted content, border, input, focus ring, primary action, destructive action, and operational status. Teal is the provisional product accent until approved brand guidance replaces it through the semantic token layer. Success, warning, information, and destructive colors are reserved for meaning and SHALL also include visible text or accessible labels. Feature code SHALL NOT encode meaning through color alone.

Light and dark palettes SHALL meet WCAG AA contrast for ordinary text and interactive labels. Theme selection MAY be stored locally because it is non-sensitive preference data. Motion SHALL be limited to feedback and state transitions and SHALL honor `prefers-reduced-motion`. The radius system SHALL use 8-pixel controls, 12-pixel surfaces, and pill shapes only for status or categorization.

Geist Variable and Noto Sans Arabic Variable SHALL be bundled with the frontend rather than fetched from an external font service. The component configuration SHALL be RTL-ready, use logical layout properties, and use Phosphor as its single icon family. A later localization task will provide translated content and change the document language and direction at runtime.

**Rationale:** Repository-owned primitives and semantic tokens make the design durable without freezing product workflows into a third-party theme. Self-hosted Latin and Arabic fonts, explicit focus states, predictable control sizes, and restrained motion support healthcare usability and future bilingual delivery.

### 2. PostgreSQL and Kysely

PostgreSQL SHALL be the transactional system of record. Local and initial production environments SHALL use the PostgreSQL 17 major-version family so Docker development, backup/restore rehearsal, and AWS RDS production remain compatible. The API SHALL use `pg` and Kysely for type-safe, explicit SQL. Each module SHALL own its data-access services; SQL SHALL not be placed in controllers. Migrations SHALL be reviewable, ordered, forward-compatible Kysely migrations. Synthetic seed commands SHALL be idempotent and SHALL refuse to run when `NODE_ENV=production`.

**Rationale:** Explicit PostgreSQL queries, constraints, transactions, row locking, JSONB audit snapshots, and reporting queries are more predictable for clinical and financial workflows than a general-purpose ORM abstraction.

### 3. Authentication and authorization

Amazon Cognito User Pools SHALL be the initial authentication boundary. One shared synthetic staging workforce identity boundary in Asia Pacific (Mumbai) (`ap-south-1`) SHALL serve local, development, and staging until customer onboarding requires stronger lower-environment isolation. Production identity resources SHALL remain separate in AWS Middle East (UAE) (`me-central-1`). The HIS SHALL retain its own application user profile, organization/facility membership, permissions, and approval limits, but SHALL not store workforce passwords.

- A person SHALL have one global application-user record. The user MAY have multiple identity bindings and multiple independently scoped tenant, organization, practice, and facility memberships. Identity bindings SHALL use the configured connection and immutable provider issuer/subject identifiers; email addresses SHALL NOT be used to automatically merge accounts.
- A tenant SHALL be the independent customer security boundary. A tenant MAY contain a parent organization or practice group, child practices, and facilities. Parent administrators MAY manage descendant memberships only through an explicit delegated permission. Clinical or financial record access SHALL NOT be inherited merely because a user belongs to a parent organization.
- Non-federated workforce accounts SHALL be invited or approved through the HIS administrator workflow; public self-registration is prohibited. Approved federated connections MAY create and update users and tenant memberships just in time. Authentication alone SHALL NOT grant a role or permission.
- The HIS database SHALL own workforce account lifecycle state. A backend-only provider adapter SHALL perform the corresponding external account operation after an authorized HIS lifecycle command, and the relevant identity binding SHALL persist a safe provider-sync outcome (`pending`, `synchronized`, or `failed`) with timestamps and an error classification where applicable. A failed provider operation SHALL never override HIS membership, role, permission, scope, session, or authorization state; it SHALL be observable for authorized remediation. The frontend SHALL neither call nor receive a provider SDK, provider token, or provider-specific account status.
- Native workforce users SHALL sign in with their real verified email address, compared case-insensitively. The platform SHALL NOT manufacture `@uae-health.com` or tenant-domain email-style usernames unless that address is an actual mailbox controlled for the user. Provider type, tenant, practice, facility, and role SHALL be application authorization data and SHALL NOT be encoded into a username.
- Workforce accounts SHALL require phishing-resistant authentication when approved or, initially, password plus TOTP authenticator-app MFA. SMS, WhatsApp, and email are not acceptable as the sole provider factor.
- Cognito MAY federate approved tenant-specific OIDC or SAML workforce providers such as Microsoft Entra ID and Okta. Cognito SHALL authenticate identities only; the API SHALL make authorization decisions from current HIS memberships, roles, permissions, approval limits, and record context.
- Site administrators SHALL own the global permission catalogue and immutable, clonable global role templates. Authorized practice administrators MAY assign global roles and create tenant-local roles from delegable permissions. Role assignments SHALL be scoped to a membership and, where applicable, an organization or facility. Administrators SHALL NOT grant permissions outside their administrative scope or delegation ceiling.
- Roles MAY be marked requestable. Role requests SHALL require an authorized approval when configured, SHALL prevent self-approval where separation of duties applies, and SHALL produce an audit trail. Neither external IdP group claims nor SCIM group membership SHALL directly grant HIS authorization; a configured mapping MAY create a pending role request.
- A tenant MAY configure SCIM 2.0 provisioning against an HIS-owned, tenant-scoped API. SCIM MAY create, update, suspend, and restore the tenant membership and approved profile fields, but SHALL NOT supply application permissions. Suspending one tenant membership SHALL NOT disable the global user or memberships in other tenants.
- Static Cognito, IAM, encryption, logging, and secret-management infrastructure SHALL be defined in the infrastructure Terraform repository. Tenant-specific identity-provider connections created or updated through the HIS administrator UI are runtime resources owned by the application control plane and SHALL NOT be simultaneously managed as static Terraform resources.
- Workforce administration endpoints SHALL resolve the validated provider connection, issuer, and immutable subject to the current HIS application user and evaluate current database-backed lifecycle state, memberships, role assignments, permission grants, validity periods, and organization scope on every request. The frontend SHALL NOT be trusted to assert administrative scope. Directory and authorization responses SHALL use HIS lifecycle and provider-sync data only; they SHALL not fetch or expose provider-specific account status. A missing active identity binding or permission SHALL fail closed and provider groups or other token claims SHALL remain irrelevant to authorization.
- A native workforce invitation SHALL validate the administrator's current database-backed organization scope before creating or looking up a Cognito account. Cognito SHALL send the administrator-created account's initial email invitation. The approved administrator action creates an active practice membership with no role assignment; default-deny authorization remains in effect until an authorized administrator separately assigns a role and any required facility scope.
- A native invitation MAY reuse an existing Cognito account only by resolving its immutable Cognito subject to one unambiguous global application user. A matching email address in the HIS without that immutable binding SHALL NOT merge users. The application-user, target-tenant identity binding, practice membership, and required audit event SHALL commit in one serializable PostgreSQL transaction. If that transaction fails after this operation created a new Cognito account, the API SHALL attempt best-effort compensation only when the failure is not a known concurrency or identity conflict and an immediate database check shows the subject remains unbound. It SHALL never delete a pre-existing account and SHALL skip deletion when that binding check cannot safely complete. Staging invitations SHALL use only controlled synthetic or test mailboxes.
- An authorized administrator MAY suspend or restore only an active or suspended membership inside the administrator's current organization scope. The change SHALL update the membership, revoke active server sessions for the target's Cognito subjects, and commit required audit evidence in one serializable database transaction. It SHALL not disable the global application user, change the Cognito account, alter unrelated practice memberships, or grant a role. Restoring a membership re-enables only its pre-existing, otherwise valid assignments; it does not create a new role or facility assignment. Administrators SHALL NOT change their own membership state through this workflow.
- An authorized administrator with current `tenant.roles.manage` permission MAY assign or revoke a global role only for another active membership inside the administrator's current organization scope. The initial role-assignment slice SHALL be practice-scoped: it SHALL neither set facility scope nor create or edit tenant-local roles. It SHALL offer only active global roles whose permissions are all marked delegable, and SHALL reject self-mutation, inactive/revoked target memberships, tenant-local roles, non-delegable roles, duplicate active assignments, and scopes outside the actor's current authority. Role assignment or revocation and required audit evidence SHALL commit in one serializable transaction; it SHALL not modify Cognito users, groups, tokens, or sessions because HIS authorization is evaluated from current database state on each protected operation.
- The tenant-local role slice SHALL allow an administrator with current `tenant.roles.manage` to create an active tenant-owned role containing one or more currently delegable global-catalogue permissions, then assign or revoke that role for another active membership in the administrator's exact current practice. The API SHALL generate the internal role code, require a unique trimmed role name per tenant, and mark local roles `admin_only` until role-request approval is implemented. It SHALL reject undelegable or unknown permissions, cross-tenant roles, self-mutation, inactive targets, duplicate active assignments, facility scope, descendant scope, role editing, retirement, deletion, and any Cognito mutation. Role definition, permission grants, role assignments, revocations, and their required safe audit events SHALL use serializable database transactions.
- An administrator with current `tenant.roles.manage` SHALL have a separate, read-only role catalogue reachable through authenticated application navigation for the current tenant and practice. It SHALL show active global templates and that tenant's active local roles, their permissions, whether a role is delegable through the current practice workflow, and a current-practice assignment count. Roles outside the actor's delegation ceiling SHALL be visibly read-only. The catalogue SHALL not disclose another tenant's local roles, assignments, members, or counts, and listing it SHALL not mutate authorization state.
- A reusable, provider-neutral authorization decision service SHALL resolve the authenticated principal to one active application user and evaluate current membership, required permission, organization scope, and facility scope from the HIS database for every protected operation. A facility-scoped operation SHALL require an active membership-facility link and an active assignment either scoped to that facility or to its organization; a confidential-record operation SHALL additionally require `confidential-records.read` in the same applicable scope. The service SHALL fail closed and accept an immutable action, opaque target identifier, organization, and optional facility from the trusted calling module rather than expose a user-controlled authorization-probe endpoint. A denied sensitive decision SHALL write safe audit evidence with the requested scope and no clinical content; a failure to write that evidence SHALL not permit the operation.
- Authentication SHALL be consumed through a provider-neutral workforce identity boundary. A dedicated identity-provider module SHALL contain the Cognito native-account and token-verification adapter; Okta, Entra ID, and other approved OIDC/SAML providers MAY be configured connections or later adapters. Other application modules SHALL depend only on provider-neutral principal and lifecycle contracts, never Cognito SDK types, Cognito-specific field names, or AWS APIs. Durable identity and session contracts SHALL identify the connection, immutable issuer, and immutable provider subject rather than treating a Cognito-specific identifier as a permanent user key. A provider migration SHALL run old and new connections in parallel and link identities only through an approved immutable-identity flow; it SHALL never automatically merge by email. Native password hashes and TOTP secrets SHALL not be copied between providers. Migration SHALL use an approved new-password activation, provider-supported one-time migration, or parallel federation transition, with MFA re-enrollment where required.
- The AWS account opt-in for `me-central-1` SHALL be managed by a separate account-level Terraform root before production regional resources are planned. One reusable Terraform workforce-identity module SHALL define the common pool, app-client, and IAM policy behavior. Independently state-managed regional callers SHALL instantiate one staging boundary in `ap-south-1` for local, development, and staging use and, when resumed, a separate production boundary in `me-central-1`. The approved production creation attempt on 2026-08-24 reached Cognito but failed with an AWS `InternalErrorException`; the user then deferred production enablement so application work can continue against staging. Production SHALL remain disabled in reviewed Terraform source until the user explicitly resumes task `3.1b`. The empty local and development pools created under the superseded isolation decision SHALL be retired through two reviewed Terraform applies: first disable deletion protection, then remove the resources from configuration.
- Each workforce pool SHALL disable public self-registration, require administrator creation, require password plus software-token TOTP MFA, use real verified email as a case-insensitive sign-in identifier, protect the pool from accidental deletion, and issue short-lived access and ID tokens through a public app client with no client secret. The public client SHALL support SRP for application sign-in; an AWS-authorized administrator password flow MAY be enabled for automated infrastructure verification because it still requires AWS credentials and is not available to an unauthenticated browser.
- The API SHALL accept only Cognito access tokens issued by the configured user pool for the configured app client. It SHALL validate the signature against Cognito's published keys, issuer, client identifier, token use, and expiry, then expose only the immutable Cognito subject as the authentication identity. Cognito groups or other token claims SHALL NOT become HIS permissions. Pool identifiers and client identifiers are configuration, not secrets; no client secret SHALL be generated or stored for this public client. Cognito user-pool encryption at rest is service-managed, while account-level control-plane logging remains an AWS account concern until the production logging task defines its retention and destination.
- The native workforce browser sign-in flow SHALL keep Cognito SRP, administrator-issued temporary-password, software-token enrollment, and software-token challenge handling in the existing memory-only browser client. Immediately after successful Cognito authentication, the browser SHALL send the short-lived Cognito access token once to the API session-exchange endpoint. The API SHALL validate the token and exchange it for an application session; the browser SHALL then sign out the Cognito SDK object, clear its memory storage, and retain no Cognito access, ID, or refresh token. Federated Entra ID, Okta, and other OIDC/SAML authentication SHALL continue to use standard browser redirects; customer IdP passwords SHALL never pass through the HIS API.
- The browser SHALL receive only a cryptographically random opaque session identifier in a host-only `HttpOnly`, `Secure`, `SameSite` cookie and a non-secret CSRF value after session restoration. The database SHALL store only a hash of the session identifier, a hash of the CSRF value, the immutable Cognito subject and client identifier, safe display metadata, expiry metadata, revocation state, and operational session timestamps. The session identifier SHALL contain no identity or authorization data. Local HTTP development MAY use an explicitly non-secure local cookie name, but staging and production SHALL fail configuration if secure cookies are disabled.
- Workforce sessions SHALL use a configurable sliding idle timeout of 30 minutes by default and a fixed absolute timeout of 8 hours by default. Valid authenticated API activity MAY extend the idle expiry and renew the cookie, but SHALL never extend the absolute expiry. Static UI asset requests SHALL NOT extend a session. The HIS session becomes the authentication continuity boundary after token exchange; current HIS authorization remains database-backed on protected operations, and user suspension or security response SHALL revoke applicable server sessions.
- Cookie-authenticated state-changing requests SHALL validate the allowed Origin and a session-bound CSRF value. Sign-out SHALL revoke the server-side session and clear the browser cookie. Session lookup, renewal, expiry, and revocation SHALL fail closed. Cognito tokens and application session identifiers SHALL NOT be placed in local storage, session storage, URLs, application logs, browser-readable cookies, or frontend runtime configuration. Authentication telemetry and audit evidence SHALL contain only safe outcome classifications, correlation, immutable subject after successful verification, and operational timestamps; it SHALL exclude submitted credentials, raw provider errors, tokens, session identifiers, and MFA secrets.
- CloudFront SHALL continue to serve only static application assets and SHALL NOT become the workforce session or authorization authority. Lambda@Edge SHALL NOT store refresh credentials, resolve HIS membership permissions, or replace the UAE-resident API session boundary. The frontend MAY call a separate API origin with credentials enabled and an exact CORS allow-list; the session cookie remains host-only to that API origin.
- UAE PASS MAY be offered as an optional patient or provider identity provider only after service-provider onboarding and approval.
- Patient WhatsApp OTP is a convenience proof of phone control, not verified clinical identity. It SHALL NOT automatically link a person to a patient record or grant provider access.
- Patient portal identities SHALL use a separate Cognito User Pool, app client, and token issuer from workforce identities because patient and workforce registration, recovery, MFA, federation, authorization, and risk policies differ. A person who is both a workforce user and a patient MAY use the same real email address in both pools, but the identities SHALL remain distinct and SHALL NOT be merged by email. The API SHALL classify the principal from the trusted issuer and immutable `sub`; a patient portal identity SHALL link to a clinical patient record only through an approved, auditable identity-proofing workflow.

**Rationale:** Keeping authentication at Cognito and authorization in the HIS permits immediate membership suspension, practice-local roles, approval workflows, multi-practice users, and record-aware enforcement without relying on stale token claims. Separate identity bindings preserve one person-level user while preventing unsafe email-based account merging. An explicit tenant hierarchy supports practice groups without allowing parent membership to imply access to child patient data.

### 4. Audit design

The platform SHALL use one append-only `audit_events` table for policy-selected clinical, financial, identity, and authorization operations rather than a history table for every business table. Required audit writes SHALL occur in the same database transaction as the corresponding sensitive mutation.

An audit event SHALL include actor, effective user, facility, entity type and opaque entity ID, action, outcome, occurred-at time, correlation ID, required reason, and safe `before_data` and `after_data` JSONB snapshots where policy permits. Database privileges and application roles SHALL prevent normal update or deletion of committed events.

### 5. UAE production residency

Production health-data workloads SHALL use AWS Middle East (UAE) (`me-central-1`). PostgreSQL primary instances, replicas, backups, snapshots, document storage, audit data, and health-data logs SHALL remain in the UAE. Production API and worker compute SHALL also run in the UAE because they process protected health information.

This decision does not itself establish regulatory compliance. Before production release, the deployment, contract, support-access model, and applicable DHA/DoH/MOHAP requirements SHALL be reviewed and approved for the customer and emirate.

### 6. Staged deployment and cost control

The pre-customer environment SHALL use only synthetic data. Developers MAY run React, NestJS, and PostgreSQL locally with Docker. Local, development, and staging AWS dependencies SHALL use `ap-south-1`; they MAY share the staging Cognito workforce pool and client while data stores, runtime credentials, and business-data configuration remain appropriately isolated. A public fake-data demonstration MAY use the existing self-managed Singapore server for one API instance and one PostgreSQL instance without an Application Load Balancer.

The repository-root Docker Compose workflow SHALL be the authoritative local entry point. It SHALL start the web application with Vite hot-module reload, the API with development reload, and PostgreSQL 17 using a named persistent volume without requiring production credentials. Normal `docker compose down` and container replacement SHALL preserve that volume. pgAdmin 9.17 MAY be enabled through an optional `tools` profile; it SHALL bind only to the local loopback interface, pre-register only the synthetic local server without its database password, and SHALL NOT contain production endpoints or credentials. The core application stack SHALL remain usable without pgAdmin.

The smallest persistent public-demo database MAY be a self-managed PostgreSQL container on the same Singapore demo server, using an encrypted persistent volume. It is a temporary, single-host pattern and SHALL contain synthetic data only. It SHALL use the same PostgreSQL version family, Kysely migration history, schemas, and backup/restore commands as the later production service.

Database evolution SHALL use forward-compatible, versioned migrations. When a real-data deployment is approved, the team SHALL provision the production PostgreSQL service in AWS UAE, take and verify a backup, rehearse the migration using a restore or logical replication, place the demo database into controlled read-only maintenance for cutover, verify row counts and migration history, and retain the old database until the approved rollback window ends. The team SHALL NOT replace a database volume or run destructive schema synchronization as an upgrade strategy.

The production web application SHALL be a static React build in a private S3 bucket in AWS UAE, delivered through CloudFront with Origin Access Control, HTTPS, a custom domain, and an ACM certificate. CloudFront SHALL serve only static public application assets; it SHALL NOT cache API responses, authenticated HTML, session data, or patient data.

The production API SHALL run behind a private origin and a production-grade TLS edge/load-balancing configuration. Load balancing, WAF, multi-instance compute, Multi-AZ PostgreSQL, backup verification, and active monitoring become mandatory before processing real customer health data.

GitHub Actions SHALL be the deployment control plane. A push to `develop` SHALL build and deploy only the synthetic-data staging environment to the existing Singapore Linux server using the Portal-style SSH deployment pattern. A push to `main` SHALL deploy the verified production release to AWS UAE. Feature branches SHALL run checks but SHALL NOT deploy automatically. Each deployment SHALL use a source-revision-tagged API image and a source-revision-tagged frontend build, run a health check before activation, and retain the prior compatible release for rollback.

Terraform state mutation and cloud resource changes SHALL run only from the infrastructure repository's manually dispatched, commit-pinned GitHub Actions workflows. Developer workstations and agent sessions MAY run formatting, validation, planning, plan display, and read-only state inspection, but SHALL NOT run Terraform apply, destroy, import, or state mutation commands. A workflow apply SHALL consume the immutable plan artifact from its reviewed plan run and verify that the plan commit matches current `main`.

Staging and production SHALL use the same CloudFront delivery pattern but SHALL NOT share a CloudFront distribution, origin, cache namespace, certificate binding, or hostname. The staging hostname (for example, `stage.example.com`) SHALL point to a staging distribution with only synthetic static content. The production hostname (for example, `app.example.com`) SHALL point to the production distribution with its private UAE S3 origin. CloudFront SHALL NOT proxy or cache API or patient data in either environment.

All infrastructure SHALL be defined as code. Disposable AWS test resources SHALL be controlled as follows:

- A stopped EC2 instance stops compute billing but can retain EBS-volume and allocated-IP charges.
- A stopped RDS PostgreSQL instance continues storage and backup billing and automatically starts after seven days.
- An Application Load Balancer cannot be stopped; it SHALL be deleted to stop its hourly and capacity-unit charges.
- Deleting a database requires an approved retained snapshot if its synthetic test data must be restored; retained snapshot storage remains billable.
- CloudFront and S3 have no server process to stop; their small inactive static-site usage is expected to remain low.

Disposable resources SHALL be destroyed when unused, except for deliberately retained storage or snapshots. Cost budgets and alerts SHALL detect unexpected remaining charges.

### 7. Engineering workflow and decision traceability

OpenSpec SHALL remain the repository source of truth for agreed scope and delivery. The program-level `initial-his-prd` change records the broad roadmap. A focused change such as `platform-foundation` owns the detailed implementation checklist so the same work is not independently tracked in multiple places.

Within a focused change:

- `proposal.md` records the problem, scope, and intended outcome.
- `design.md` records accepted technical decisions, constraints, rationale, and consequences.
- capability specs record normative requirements and testable scenarios.
- `tasks.md` records ordered implementation work and its verified completion.

If a discussion introduces additional implementation work, it SHALL be added as a new task with a stable identifier rather than silently folded into a completed task. If an accepted discussion changes architecture, security, data handling, deployment, or another implementation constraint, the design and any affected capability spec SHALL be updated with the implementation. Questions that do not produce an accepted decision do not require a design update.

A task SHALL be presented for user review only after its code and documentation are complete and applicable verification passes. The agent SHALL summarize the diff and checks, explicitly request approval to commit and push, and stop before either operation. Approval SHALL be specific to the current task and SHALL NOT carry forward from prior tasks. If approval covers only committing, pushing requires a separate approval. Once approved, the task checkbox SHALL be marked complete in the task-numbered commit, using `task <task-id>: <imperative summary>`, and the commit SHALL be pushed only when the user has approved the push. Failed, incomplete, or unapproved work SHALL not be marked complete, committed, or pushed. Force-pushes are prohibited.

The repository SHALL use `develop` as the integration branch that deploys synthetic data to staging and `main` as the protected production-release branch for AWS UAE. Ordinary development SHALL not be pushed directly to `main`. The initial uncommitted repository state MAY be captured in one task-numbered baseline commit; subsequent unrelated tasks SHALL use separate commits.

## Consequences

- The former MariaDB/TypeORM approach is superseded by PostgreSQL/Kysely.
- Cognito provides the initial low-operations identity service while preserving future OIDC/SAML and UAE PASS integration paths.
- One global application user can work across approved practices while every membership, role assignment, and authorization decision remains tenant- and facility-scoped.
- Practice-specific IdP and SCIM onboarding becomes application control-plane behavior; Terraform owns the shared AWS foundation rather than dynamic customer configuration.
- CloudFront reduces static-site operations but does not proxy or cache protected API data.
- A public demo on the existing Singapore server is permitted only with fake data; it is not a healthcare production deployment.
- New decisions and evolved work remain traceable through focused OpenSpec design, specs, tasks, and task-numbered commits.
